# Project Rules — Homework 2 Piano

## Scope and data

- Preserve all 88 keys from A0 to C8: 52 white keys and 36 black keys; A4 = 440 Hz.
- Allow at most 8 held voices and replace the oldest voice using FIFO. Explain the 40 ms release tail separately.
- Preserve note-on order, delta, duration, and overlapping notes in recordings; support playback at 0.5×, 1×, and 2× speed.
- Do not change requirements or remove features merely to make tests pass.

## React and code quality

- Use function components, Hooks, createRoot, and event.key. Do not use Class components, ReactDOM.render, defaultProps, keyCode, or alert(). Audio-related business logic classes are allowed.
- Do not mutate React state directly; copy Sets and recording snapshots before storing them in state.
- Keep callbacks stable, pass simple props to individual keys, and use React.memo for PianoKey.
- Separate the synthesizer, recorder, and playback queue from the UI. Handle errors and clean up listeners, timers, and audio nodes when they are no longer needed.

## Responsive design and accessibility

- Prevent horizontal scrolling in both the page and child regions at 375px; do not hide layout problems with overflow-x: hidden.
- Keep all 88 keys accessible through wrapping octave groups; allow text in the recording table to wrap.
- Use semantic HTML. Use div elements only when needed to group layout content.
- Associate form controls with label htmlFor and an id generated by useId; give buttons accessible names.
- Declare lang="vi"; support Tab, Space, and Enter, provide visible focus indicators, and handle overlapping activation sources without stopping notes prematurely.
- Target a Lighthouse Accessibility score of 100; distinguish automated results from manual WCAG checks.

## Security

- Render data as text through JSX. Do not use dangerouslySetInnerHTML, innerHTML, document.write, eval, or new Function to process data.
- Do not execute data from URLs, storage, or external sources; validate note data before playback.
- Do not commit tokens, passwords, node_modules, or dist to Git.

## Verification and AI use

- Read and verify AI-proposed code; do not treat an AI explanation as evidence that code has actually been executed.
- Audits must identify the before and after versions, reproduction steps, expected and actual behavior, root cause, fix, and reproducible verification results.
- Do not fabricate defects, prompts, screenshots, or logs, or insert defects into a baseline to manufacture evidence. State the limitation when AI provenance cannot be established.
- Run unit tests, build, and lint after functional changes; use browser checks for interaction and layout defects.
- Give each commit one clear purpose and inspect staged changes. Commit only files within lab3/homework2, without including changes from other assignments.
- Do not rewrite history, backdate commits, or create artificial commit splits to meet a count. These rules were added on 8 November 2026; do not claim they existed from the start of the project.
